# v0.7 Participant Accounts & Server Persistence

Current production remains https://stempathai.com on Vercel, in LOCAL / auth-disabled mode. This release does not change DNS, activate ECS, purchase services or depend on ICP approval. The same source supports a later Ubuntu / Docker / Nginx / PostgreSQL deployment.

## Configuration and rollout

| Mode | PERSISTENCE_MODE | AUTH_MODE | Database required |
|---|---|---|---|
| Current prototype (default) | local | disabled | No |
| Future authenticated pilot | postgres | participant | Yes |

Unset variables default to local/disabled/OPEN. Postgres without participant auth, or participant auth without Postgres, fails closed rather than falling back to anonymous storage. Never expose postgres mode until migrations, bootstrap, HTTPS, trusted ingress and restore testing are complete. Missing DATABASE_URL must not affect LOCAL builds. Server-only variables are never NEXT_PUBLIC variables.

STUDENT_TASK_MODE=OPEN permits task browsing/custom projects. ASSIGNED limits student starts to the exact researcher-assigned task revision. Assignment stores the research condition and full policy (including capture OFF by default). Existing projects retain their original assignment snapshot/policy when a later assignment changes. Custom learner task drafts are temporary in account mode; the task snapshot is durable once a project starts. The local teacher library remains available in LOCAL mode.

## Accounts and PINs

Each user has a random internal UUID, unique normalized uppercase participant code, pinHash, STUDENT/RESEARCHER/ADMIN role, ACTIVE/DISABLED status and timestamps. Codes begin with a letter and contain letters, digits or hyphens (2–32 characters). No names, emails, phones, student numbers, birthdays or public registration are required. Codes are pseudonyms; a researcher may maintain a separate mapping under their study procedures outside STEMPath.

Node's built-in scrypt uses N=32768, r=8, p=3, a random 16-byte salt and 64-byte output. Comparisons use timingSafeEqual. Random distribution PINs have six digits; the initial privileged PIN must have 8–12 digits. These cost parameters follow the [OWASP scrypt guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). This is a supported password KDF, not a fast checksum. PINs are sent only over the same-origin login/create/reset flow, never localStorage or research exports. No logging of PINs or credential payloads is introduced. The researcher sees a generated/reset PIN once in component memory, can explicitly download a distribution CSV and hide it. The database retains only the hash; lost PINs must be reset. Do not retain distribution sheets alongside research exports.

Researcher/admin APIs can create one student, atomically generate 1–100 students, reset a PIN, disable a student, view project status, assign a task/revision/policy, export codes and export research data. They cannot create privileged accounts through a student-generation request. Normal students cannot access these functions. The initial ADMIN is created with the explicit operator-only `pnpm db:bootstrap` command; it refuses when a privileged account already exists. It prompts for credentials instead of taking them in shell arguments. Its PIN entry is visible in the operator terminal: run privately, without terminal recording. Later privileged account provisioning is deliberately an operator procedure, not a public registration endpoint.

## Sessions and security boundary

Login issues 32 cryptographically random bytes. Only an HMAC digest is stored in auth_sessions; the browser gets an HttpOnly, SameSite=Lax cookie, Secure in production, path /. Sessions expire after eight hours; logout deletes the digest and clears the cookie. Reset and disable revoke all sessions for that user. Every authenticated request checks account status. SESSION_SECRET must be independently generated with at least 32 characters; rotation invalidates all active cookies. No authentication tokens go into browser storage or research exports.

Login attempts have database-backed atomic fixed-window counters: five attempts per code and twenty per ingress IP in fifteen minutes. These count successful attempts too, conservatively. Expiry restores access, with no permanent lock. Missing codes perform the same expensive hash work. Hash keys use SESSION_SECRET; raw IPs are not retained. Cleanup removes old counters. TRUST_PROXY=false ignores forwarding headers and uses a shared ingress bucket, which is conservative but may inconvenience a classroom. Before an ECS pilot, set TRUST_PROXY=true only when Nginx overwrites client forwarding headers and direct app access is blocked. Account reset clears its code counter, not a shared IP counter.

All mutations require the expected Origin; reads and responses use no-store. Services use parameterized SQL and explicit owner filters. Student/admin identity comes from the cookie, never body-supplied userId. UUID path parameters and JSON body sizes are validated. Unauthenticated project APIs return 401; foreign projects/messages/research return 404. Admin role checks apply to each admin API and task-check calls. The chat route authenticates, loads the owned project, replaces browser task/policy with the server snapshot and rejects NO_AI. AI history remains bounded. This release does not claim authenticated research telemetry is tamper-proof: learner records and client event measurements still originate in the client.

## PostgreSQL model and migrations

Drizzle provides the schema and explicit SQL migration history; node-postgres supplies pooled, parameterized queries and transactions. `pnpm db:generate` generates SQL/snapshots; `pnpm db:migrate` applies them through the Drizzle migrator. Do not manually edit production tables or use schema push in place of migration review. The initial migration is in `drizzle/0000_unknown_landau.sql` with generated metadata. Migration history makes repeated deployment reproducible. Run migrations as a separate operator/deployment step, not during an anonymous Vercel build.

Normalized tables: users, auth_sessions, login_limits, task_definitions (immutable revision snapshot), task_assignments, projects, project_stage_state, messages, learning_records, research_sessions, research_events. Foreign keys and cascades prevent orphaned learner rows. Owner, stage-order, expiry and task-revision indexes support the principal reads. A project belongs to one user and one immutable task revision. Seven canonical stage IDs and levels 1/2/3 remain unchanged. Stage status is derived from the v0.6.2 core records (NOT_STARTED/IN_PROGRESS/READY/COMPLETED), never a mastery judgment. Notebook and per-stage AI Challenge state are retained.

Project updates use expected integer version, updatedAt and a transaction. Stale writes return 409 and leave the newer server state untouched. The client serializes its writes, displays failure, and requires deliberate reload before replacing unsaved edits; it does not silently merge divergent device edits. The database is authoritative. Account mode never imports anonymous local projects or automatically replays another user's browser cache. Browser tab sign-in/sign-out notifications clear the prior account UI. There is no account-mode local conversation cache or PIN storage. Logout waits for pending saves; failed saves keep the workspace open for retry. An abrupt tab close/network failure before the save completes may still lose an unsaved edit. Use the Saved indicator before closing.

Full learner-visible messages are retained and restored; only visible fields are persisted, not system prompts, API secrets or authorization headers. AI requests still include only bounded recent history (8 messages / 8,000 characters), current task/stage/support and structured records. There are no paid readiness or summarization calls. Failed student turns remain; reloading does not retry AI automatically. Images still use transient object URLs and are not database/Blob uploads.

## Research privacy and linkage

Research sessions have server foreign keys to user/project plus their existing pseudonymous research snapshot. Research events are normalized and linked to the session. Resuming restores the latest session/usage and records WORKSPACE_RESTORED. Separate research versions reject conflicting device snapshots. Research schema remains 0.6; app version is 0.7 and prompt version remains young-learner-v3; older archives remain supported.

Learner conversation storage and research capture are distinct. Server assignment policy controls storeMessageText. OFF prevents raw message/artifact text entering research JSON/CSV even though learning messages are durable. A participant cannot change this policy or another participant's code. Export whitelists research fields; internal user IDs, PIN hashes, cookies and security metadata are not included. Project-status management does not expose raw conversations. There is no bulk raw-conversation review endpoint. Opted-in research text can be exported only through a researcher/admin endpoint. Study consent, access policy and lawful retention remain researcher responsibilities.

## Deletion and recovery

Account deletion requires a deliberate dialog plus exact `DELETE <participantCode>` confirmation. STUDENT deletion cascades projects, stages, messages, records, research sessions/events, assignments and login sessions. The code cooldown is removed. Unreferenced learner-created task snapshots are deleted; shared curricular snapshots remain with no deleted-user identity. Project removal separately warns that linked research records are removed. Server Restart creates a fresh project and retains the original study project, rather than silently erasing research. Disable is reversible through an operator procedure; re-enable UI is not included. Backups/distributed credential sheets are separate retained copies and must follow the study retention policy.

## Docker and future ECS

Dockerfile has dependency, migration/tooling, Next.js builder and unprivileged standalone runner stages. docker-compose.yml provides app + postgres + one-shot migrations and a durable database volume. Database has no public host port. App binds only 127.0.0.1:3000 for Nginx. No production secrets are committed; .dockerignore excludes all real env files and build artifacts. Set POSTGRES_PASSWORD, DATABASE_URL (host `postgres` inside Compose), SESSION_SECRET and later AI variables in an untracked, restricted .env. Compose refuses missing secrets. The app image builds in LOCAL mode and reads authenticated mode at runtime. Next.js uses standalone output for Docker/ECS and standard output when VERCEL=1, allowing Vercel's own adapter to package its server functions. Both retain the same application/API source. See the [official Next.js deployment options](https://nextjs.org/docs/app/getting-started/deploying).

Future sequence after ICP approval:

1. Prepare Ubuntu, Docker/Compose and Nginx; firewall direct app/DB access; provision enough RAM for PostgreSQL, Next.js and scrypt.
2. Generate secrets privately, initialize the volume and run `docker compose up -d --build`. Migration failure must block app startup.
3. Run `docker compose run --rm migrate pnpm db:bootstrap` privately for the initial ADMIN.
4. Verify migrations, participant isolation, two-device restoration, reset/logout, assignment NO_AI, backups and the absence of secrets in logs.
5. Configure HTTPS and Nginx before exposing participant auth. Nginx must set `Host $host`, `X-Forwarded-Proto $scheme` and `X-Forwarded-For $remote_addr` (overwrite, not append untrusted values). Then enable TRUST_PROXY=true.
6. Run a supervised account pilot and a database restore drill. Switch DNS only in a separate explicitly approved infrastructure task. Vercel remains current production until then.

No RDS/OSS purchase, domain change or ECS activation is performed in this release.

## Backups

Daily encrypted backups are recommended, with monitoring and an off-host copy under an approved retention/access policy. Example operator commands (paths and retention must be configured):

```sh
umask 077
docker compose exec -T postgres pg_dump -U stempath -d stempath -Fc > /secure-backups/stempath-YYYY-MM-DD.dump
# Restore into a separate isolated database; never overwrite live production for a test.
docker compose exec -T postgres createdb -U stempath stempath_restore_test
docker compose exec -T postgres pg_restore -U stempath -d stempath_restore_test --no-owner < /secure-backups/stempath-YYYY-MM-DD.dump
```

Check dump success/size, run periodic restore tests, encrypt/restrict files, define retention and perform deletion in backup lifecycle too. Do not commit dumps, database volumes, .env or distribution CSVs. Backups contain hashes and learner text even if research capture is OFF.

## Validation and limitations

Tests use an isolated PGlite PostgreSQL engine locally; CI uses an actual PostgreSQL 17 service through TEST_DATABASE_URL and refuses databases not named stempath_test. Both use the same committed Drizzle migrations. CI runs lint, typecheck, all tests, LOCAL build, app/tooling Docker builds and Compose validation with disposable credentials. AI_PROVIDER=demo; paid DeepSeek is not called by CI.

The first small pilot intentionally omits account self-registration, personal identifiers, cross-device image uploads, production email recovery, account-role editing, assigned-task removal UI, admin pagination beyond 500 accounts, automatic conflict merging, immutable research auditing and centralized paid-usage billing/enforcement. Snapshot saves are bounded (2 MB project, 4 MB research); very large projects fail visibly instead of truncating text. Research snapshot/event replacement and full project reconciliation prioritize correctness over high-scale write efficiency; optimize after pilot measurements. Study policy changes apply to new projects, not silently to existing ones. Existing browser-only work stays local and has no automatic authenticated migration. Current Vercel must remain local/disabled; authenticated activation still requires a real deployment smoke test, HTTPS and backup recovery testing.
